# Как мы работаем с репозиторием

Правила управления конфигурацией проекта (ЛР 4). Они нужны, чтобы в любой момент было понятно: какая версия продукта актуальна, кто и зачем внёс изменение, какая задача за ним стоит и прошло ли оно проверку.

## 1. Путь изменения

```
Issue → ветка от задачи → коммиты → Pull Request → автопроверка и ревью → squash merge в main → релиз
```

1. **Задача.** Любая работа начинается с Issue на доске: с критериями готовности, оценкой, исполнителем и спринтом.
2. **Ветка.** Создаётся от актуального `main` прямо из задачи: в Issue справа **Development → Create a branch**. Одна задача — одна ветка. Ветка живёт не дольше спринта, лучше 1–3 дня.
3. **Коммиты.** Небольшие, с понятным сообщением и номером задачи.
4. **Pull Request.** Открывается, как только есть что показать. Незаконченную работу оформляйте как **Draft**. В описании `Closes #N`, заполненный чек-лист.
5. **Проверка.** Автопроверка `ci / quality` должна быть зелёной. Ревьюер — другой участник, он проверяет по чек-листу из `docs/quality-plan.md`.
6. **Слияние.** Кнопка **Squash and merge**: в `main` попадает один коммит на задачу. После слияния ветка удаляется, задача закрывается автоматически.
7. **Релиз.** В конце спринта менеджер создаёт релиз с автоматическими заметками (раздел 6).

## 2. Ветки

Модель — **GitHub Flow**: одна долгоживущая ветка `main` и короткие ветки под задачи.

- `main` всегда в рабочем состоянии: проверки проходят, документы согласованы. Прямые коммиты в `main` запрещены.
- Имя ветки: `<тип>/<номер задачи>-<кратко-латиницей>`.

| Тип | Когда | Пример |
|---|---|---|
| `feat` | Новая функция или пользовательская история | `feat/42-schools-300m` |
| `data` | Загрузка, очистка, обновление данных | `data/41-completeness-spike` |
| `fix` | Исправление ошибки | `fix/57-buffer-in-degrees` |
| `docs` | Документы проекта | `docs/44-risk-register` |
| `ci` | Автопроверки, workflow, настройки репозитория | `ci/45-quality-checks` |
| `chore` | Служебное: обновление из шаблона, зависимости | `chore/lab4-files` |

## 3. Коммиты

Формат: `тип: что сделано (#номер)`. Тип — из таблицы выше. Описание — коротко, в повелительном наклонении или как факт.

```
feat: add schools within 300 m table (#42)
fix: compute buffers in UTM instead of degrees (#57)
docs: update risk register after Sprint 1 (#44)
```

Один коммит — одно логическое изменение. Не смешивайте в одном коммите правку данных и правку документа.

## 4. Правила для ветки main

Настраиваются в **Settings → Rules → Rulesets** (приложение А к заданию ЛР 4):

- изменения только через Pull Request;
- нужно 1 одобрение, одобрение снимается после новых коммитов;
- все обсуждения в PR должны быть закрыты;
- обязательная проверка `quality` должна пройти;
- запрещены force push и удаление ветки;
- линейная история (squash или rebase merge).

На бесплатном тарифе GitHub правила ветки работают только в публичных репозиториях, поэтому репозиторий проекта публичный. Перед сменой видимости команда проходит чек-лист из шага 5 задания ЛР 4: в репозитории нет ключей доступа, персональных и закрытых данных.

## 5. Данные, ноутбуки и код

- **Сырые данные** (`data/raw/`) в Git не коммитим, их можно скачать заново ноутбуком 01.
- **Обработанные данные** (`data/processed/`) коммитим, если файл меньше 10 МБ. Каждый слой проходит `scripts/validate_data.py`, правила — в `data/validation.json`.
- **Новый источник** сначала описывается в `data/sources.md` (лицензия, дата, ссылка), потом используется.
- **Ноутбуки** сохраняются без вывода ячеек. В Colab: **Изменить → Очистить все выходные данные**, затем **Файл → Сохранить копию на GitHub** в свою ветку, не в `main`.
- **Расчётные функции**, которые используются в нескольких местах или влияют на цифры для заказчика, выносятся в `src/` и покрываются тестом в `tests/`.
- **Расстояния и площади** считаются только в метрической проекции (`to_metric()` из `src/geo_utils.py`).

Локальная проверка перед PR (по желанию, CI сделает то же самое):

```bash
pip install -r requirements-dev.txt
ruff check src tests scripts
pytest -q
python scripts/validate_data.py
```

## 6. Версии и релизы

- Версии: `v0.<номер ЛР>` для релизов по итогам лабораторной, `v0.6-mvp` и `v1.0` по релизному плану.
- Релиз создаёт менеджер проекта в конце спринта: **Releases → Draft a new release → Choose a tag → Generate release notes**. Заметки группируются по меткам PR, категории заданы в `.github/release.yml`. Поэтому у каждого PR должна быть метка.
- В начало заметок менеджер добавляет 2–3 предложения: цель спринта и достигнута ли она.

## 7. ИИ-ассистенты

Всё, что сделано с помощью ИИ и попало в репозиторий, записывается в `docs/ai-usage.md`. ИИ не может быть ревьюером вместо участника команды.
